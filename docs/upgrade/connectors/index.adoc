== Motivation and Background

There is a difference between connector and resource in midPoint.
Connector is a piece of code that is used to connect to a particular class of systems (e.g. "any LDAP server"). Resource is a specific system (e.g. "OpenLDAP server link:http://ldap.example.com[ldap.example.com]"). Obviously, every resource has to tell which connector it is supposed to use to reach that particular system.
As both resources and connectors are midPoint objects this is quite easy.
Resource contains xref:/midpoint/reference/schema/object-references/[object reference] to the connector: `connectorRef`. Therefore when midPoint need to reach a particular resource it will fetch resource object from the repository, look at the connectorRef reference, look up referred connector object in the reposity and that connector object points to the connector code.

The trouble is, that connector objects (xref:/midpoint/architecture/archive/data-model/midpoint-common-schema/connectortype/[ConnectorType]) are not entirely ordinary objects.
These objects refer to the connector code that resides in midPoint servers or xref:/connectors/connid/1.x/connector-server/[connector servers]. Connector objects are usually generated automatically by midPoint servers during server startup.
At that time midPoint looks for all the connectors that are locally available to that server.
This essentially means looking for JAR files that contain connector code.
When a connector is discovered then the server creates a new connector object (xref:/midpoint/architecture/archive/data-model/midpoint-common-schema/connectortype/[ConnectorType]). And this automatic generation of connector objects is kind of a trouble.
Because those objects will have unpredicatable xref:/midpoint/devel/prism/concepts/object-identifier/[OIDs]. Therefore resource definitions (xref:/midpoint/architecture/archive/data-model/midpoint-common-schema/resourcetype/[ResourceType]) cannot have fixed OIDs in their `connectorRef`s.

Fortunately, midPoint has a mechanism how to resolve a reference dynamically when an object is imported.
Therefore the usual practice is that the resourceRef does not contain fixed OID.
It contains a search filter instead.
The search filter is executed when resource definition is imported to midPoint.
The filter looks up appropriate connector object and fills in the OID.


== Bundled and Unbundled Connectors

The Identity Connectors are quite independent of the midPoint releases.

Some connectors are _bundled_ with midPoint.
Which means that they are part of midPoint code.
Those are the connectors that are almost always used in any midPoint deployment.
Such as LDAP, Active Directory or CSV connector.

Most of the connectors are _unbundled_. This means they are not distributed with midPoint.
These connectors must be downloaded separately and installed in xref:/midpoint/reference/deployment/midpoint-home-directory/[midPoint home directory] or in a xref:/connectors/connid/1.x/connector-server/[connector server]. The connectors are not bundled with midPoint for many reasons.
One of the reason is that many connectors are rarely used or even outright exotic.
Bundling them all would make midPoint distribution too big.
There are connectors that require third-party libraries to work and we simply cannot bundle them at all.
But unbundling has also a positive side: connector may have their own lifecycle.
You can upgrade the connectors without upgrading midPoint itself.
So you can use upgraded connectors that provide required features or fix outstanding bugs.


== Upgrade

When a connector is upgraded, then new connector object (xref:/midpoint/architecture/archive/data-model/midpoint-common-schema/connectortype/[ConnectorType]) is created for new connector version.
This is quite natural thing to do.
ConnId framework can support several versions of the same connector running at the same time.
And this is a very nice feature, as it allows gradual upgrades.
E.g. this is especially nice for deployments that have 100 resources with the same connector.
We definitely do not want to change the connector version for all of them at once.
The new connector version may have some changes that can break existing resources.
So it make sense test the new connector version only on a couple non-critical resources.
And roll out the upgrade only if the new connector is tested.

This method works well with unbundled connectors.
Just install a new version of the connector in addition to the old one.
The test the new version and change connector references on all resources.
Then remove the old connector version.

However, it is somehow different for bundled connectors - especially if midPoint itself is upgraded.
In that case the old connector version suddenly disappears and there is a new connector version as a replacement.
However, all the resources are pointing to the old connector versions, which is no longer there.
Filters in dynamic `connectorRef` references are not evaluated again as the resource were not re-imported.
Nothing has really changed as far as midPoint itself is concerned.
However, the references suddenly point to nowhere and the resources do not work.

There are several strategies how to deal with bundled connector upgrades:

. Be proactive and explicitly deploy old connector version to midPoint home directory as part of the upgrade process.
Therefore upgraded midPoint detects both old and new connector versions.
And the resources will work.
Then there is sufficient time to gradually upgrade the resources.

. Fix the references before any damage happens.
Suspend all the synchronization and propagation tasks before the upgrade.
Stop all user access to midPoint (e.g. by disabling load balancer).
Upgrade midPoint and start the server.
The resources will not work at this moment, but there is nothing that would attempt to work the resources right now.
Use that moment to update connectorRef references.
Then resume the tasks and let users in.

. Use the power of xref:/support/subscription-sponsoring/[platform subscription] to let us implement some smarter strategy.
There are may possibilities how midPoint can be improved.
E.g. we can support runtime or "upgrade-time" dynamic reference resolution.
Or implement smart references that points to "latest connector version".
Or have some kind of post-upgrade process to handle the references.
There are many possibilities.

Note that midPoint will not delete the old connector object even if the connector code disappears and midPoint can no longer detect the connector.
This may sound strange, but it is in fact an important safety feature.
The connector code may have disappeared by mistake, e.g. midPoint home directory is restored from an earlier backup than the database backup.
Therefore there are connector objects, but connector code is missing.
In that case we do not want to delete the connector objects.
Remember, connector object OIDs are generated.
If we would delete the objects that it will be very difficult to restore the connector references.
Especially if many custom connectors are used.
And there are too many ways how such mistakes and various corner cases can happen - and the impact is usually quite bad.
Therefore we have decided not to delete connector objects automatically.
It is no big trouble to do it manually anyway.
A connector is not upgraded every day.


=== Upgrade Procedure

This procedure describes the steps that an administrator has to take when a new version of a connector is released and it should be used in an existing deployment.
It applies to unbundled connectors as well as to bundled connectors (e.g. LDAP or Active Directory connector) that were released separately from midPoint, for example because of a security fix.
MidPoint itself is not upgraded in this procedure.

The procedure is safe to do gradually.
The old and the new version of the connector work side by side, and each resource uses the version that its `connectorRef` points to.
Nothing changes for a resource until its `connectorRef` is updated.

[TIP]
====
Try the procedure in a test environment first.
Read the release notes of the connector before the upgrade.
A new connector version may bring changes in connector configuration or resource schema.
Some connectors have dedicated migration guides, see <<See Also>>.
====

The procedure is slightly different depending on where the currently used (old) version of the connector comes from:

[%autowidth,cols="h,1,1"]
|===
| | Old version is unbundled | Old version is bundled

| Typical connectors
| Any connector that was deployed manually to the midPoint home directory.
| LDAP, Active Directory, CSV and DatabaseTable connectors that are a part of midPoint distribution.

| Where the old code is
| JAR file in the midPoint home directory.
| Inside midPoint itself.
There is no JAR file in the midPoint home directory.

| Removing the old version
| The administrator removes the JAR file and the connector object.
| Not possible.
The old version stays present until midPoint is upgraded.

| Effect of the next midPoint upgrade
| None.
The deployed JAR files stay as they are.
| The bundled version changes.
The resources that still use the old bundled version stop working until their `connectorRef` is updated.
The resources that were switched to a version deployed in the midPoint home directory are not affected.
|===

The steps 1 to 5 are the same for both cases.
The differences are in the step 6 and in what happens during the next midPoint upgrade.

==== 1. Record the Current State

. Go to _Configuration_ > _Repository objects_, select the _Connector_ type and find the connector that is currently used.
Write down its name, version (`connectorVersion`) and OID.
. Find all the resources that use the connector.
In the _Resources_ list, switch the search to the advanced (query) mode and use the OID of the current connector:
+
[source,midpoint-query]
----
connectorRef matches (oid = "5e8a944b-8e7d-4f7b-bc64-6838b804353f")
----
+
Resource templates and resources with xref:/midpoint/reference/resources/multi-connector-resource/[additional connectors] reference connectors as well.
Check `connectorRef` in those too.
. Back up the definitions of the affected resources, e.g. export them from _Configuration_ > _Repository objects_.

==== 2. Deploy the New Connector Version

. Download the JAR file of the new connector version.
Download links are listed on the page of the particular connector in the xref:/connectors/connectors/[connectors] list.
. Copy the JAR file to the `connid-connectors` subdirectory of the xref:/midpoint/reference/deployment/midpoint-home-directory/[midPoint home directory].
The legacy `icf-connectors` subdirectory works as well.
In a clustered deployment, copy the file to every node.
In a containerized deployment, make sure that the file is placed on a persistent volume or that it is part of the image, otherwise it is lost when the container is re-created.
. Do not remove or overwrite the JAR file of the old connector version.
If the old version is bundled, there is no such file in the midPoint home directory at all.
. Wait about a minute.
There is no need to restart midPoint.
MidPoint watches the connector directories, it loads the new JAR file and creates the connector object automatically.
In a clustered deployment, each node loads the file from its own midPoint home directory.

WARNING: Only adding a new JAR file is safe while midPoint is running.
Never replace or delete a JAR file of a connector that is already loaded by a running midPoint.
Always deploy the new version as a new file next to the old one.

If the connector is deployed in a xref:/connectors/connid/1.x/connector-server/[connector server], deploy the new JAR file to the connector server instead, restart the connector server and run the connector discovery on the corresponding connector host in midPoint.

==== 3. Check That the New Connector Was Discovered

Go to _Configuration_ > _Repository objects_ and select the _Connector_ type.
There should be two connector objects now, one for each version, for example:

* `ConnId com.evolveum.polygon.connector.ldap.LdapConnector v3.9` (the old version)
* `ConnId com.evolveum.polygon.connector.ldap.LdapConnector v3.9.1` (the new version)

Write down the OID of the new connector object.

If the new connector object is not there, look for errors related to the connector bundle in the midPoint log file.
The usual causes are a JAR file placed in a wrong directory, insufficient file permissions, or a connector that is not compatible with the ConnId framework version used by midPoint.

==== 4. Update the Resources

Change the `connectorRef` of the resource to the OID of the new connector object.
Start with a single, non-critical resource.

Open the resource in _Configuration_ > _Repository objects_ (or in midPoint Studio) and replace the OID in the `connectorRef` element:

.Before
[source,xml]
----
<connectorRef oid="5e8a944b-8e7d-4f7b-bc64-6838b804353f" type="c:ConnectorType"/>
----

.After
[source,xml]
----
<connectorRef oid="c80f9e96-cead-4a41-a846-999f27d94099" type="c:ConnectorType"/>
----

Change only the OID of the reference.
Do not change the OID of the resource itself.
The connector configuration (`connectorConfiguration`) usually does not need any change, as the configuration namespace does not depend on the connector version.
The namespace changes only if the connector bundle name or the connector class name has changed, which is rare and it is always described in the release notes of the connector.

If the resource definitions are maintained outside midPoint (e.g. in a version control system) and they use a search filter in `connectorRef`, make sure that the filter selects the new version, e.g. by adding a condition for `connectorVersion`, remove `connectorRef` oid, and re-import the resource.
The filter is resolved only during the import if oid is not defined.
It is never re-evaluated for a resource that is already stored in the repository.
While two versions of the same connector are installed, a filter that specifies only `connectorType` matches both of them and it is not reliable.

.Connector reference using a filter with connector version
[source,xml]
----
<connectorRef type="c:ConnectorType">
    <filter>
        <q:text>
            connectorType = "com.evolveum.polygon.connector.ldap.LdapConnector"
            and connectorVersion = "3.9.1"
            and available = true
        </q:text>
    </filter>
</connectorRef>
----

==== 5. Test the Resource

. Open the resource and run _Test connection_.
All the steps of the test should be successful.
. Check that the resource page shows the new connector version.
. If the release notes of the connector mention changes in the resource schema, refresh the resource schema.
. Verify the basic operations.
List the accounts on the resource, then preview or xref:/midpoint/reference/simulation/[simulate] a change of a test account, or reconcile a single test user.
. Watch the midPoint log file for errors.

When the first resource works well, repeat the steps 4 and 5 for the remaining resources.

To return a resource to the old connector version, simply put the OID of the old connector object back to its `connectorRef`.
This works as long as the old connector version is still installed.

==== 6. Remove the Old Connector Version

This step applies only when no resource uses the old connector version any more.
Use the query from the step 1 to verify that.

*Old version is unbundled*

. Stop midPoint.
Unlike adding a JAR file, removing a loaded JAR file requires midPoint to be stopped.
. Remove the JAR file of the old version from the midPoint home directory on all the nodes.
. Start midPoint.
. MidPoint does not delete the old connector object.
It only marks it as not available (`available` is set to `false`).
Delete the old connector object manually in _Configuration_ > _Repository objects_.

This can wait for the next planned maintenance window.
An unused connector version does no harm.

*Old version is bundled*

There is nothing to do at this point.
The old version is a part of midPoint and it cannot be removed.
Do not delete its connector object.
MidPoint would create the object again during the next start, with a different OID.
Both versions stay available until midPoint is upgraded.

==== After the Next MidPoint Upgrade

A connector JAR file placed in the midPoint home directory stays there when midPoint is upgraded.
The resources that use it keep working without any change.
This is different from the resources that use a bundled connector, which need their `connectorRef` updated after each midPoint upgrade that changes the bundled version, see xref:/midpoint/reference/upgrade/upgrade-guide/[].

Review the manually deployed versions of bundled connectors after each midPoint upgrade:

* The connector object of the old bundled version is marked as not available after the upgrade, because the new midPoint release bundles a different version.
If no resource uses it, it can be deleted now.
* If the new midPoint release bundles exactly the same connector version as the one deployed in the midPoint home directory, midPoint uses the existing connector object for it.
The resources keep working and no `connectorRef` change is needed.
The JAR file in the midPoint home directory is redundant now.
Remove it while midPoint is stopped.
* If the new midPoint release bundles a later version, switch the resources to it using this same procedure.
Then remove the manually deployed JAR file and its connector object as described in the step 6 for unbundled connectors.
* If the new midPoint release bundles an earlier version than the one deployed manually, keep the manually deployed version.

==== Troubleshooting

[%autowidth]
|===
| Symptom | Likely cause

| Resource operations fail with `The classes (JAR) of connector ... were not found by the ICF framework`.
| The `connectorRef` of the resource points to a connector object whose code is no longer installed, e.g. the JAR file was removed or a bundled connector version has changed during midPoint upgrade.
Point the `connectorRef` to an available connector object, or deploy the missing connector version to the midPoint home directory.

| The new connector object is not created.
| The JAR file was not loaded.
See the step 3.

| The resource works on some cluster nodes only.
| The JAR file is not present on all the nodes.

| Connector configuration validation fails after the change of `connectorRef`.
| The configuration properties of the connector have changed between the versions.
Check the release notes of the connector and adjust `connectorConfiguration`.
|===


== Future

MidPoint can do all kind of smart things with resources and connectors.
But most of the configuration needs to be done with XML/JSON/YAML files.
The user interface support for connector and resource configuration is somehow limited.
And this seems to be perfectly acceptable for many midPoint users.

However, there is always a possibility to extend midPoint user interface.
Especially some user interface to manage the connectors and assist connector upgrades would be useful.
Evolveum offers xref:/support/subscription-sponsoring/[subscription programs] that can be used to fill in missing midPoint functionality.
