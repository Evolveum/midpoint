= Smart Mappings Recommendation
:page-toc: top
:page-since: "4.11"
:page-upkeep-status: green

== Overview

The *smart mappings recommendation* operation proposes attribute mappings for a single resource object type (identified by resource, kind and intent).
It works on pairs of a shadow attribute and a focus property that were matched in a preceding schema matching step.
For each pair, it decides which kind of mapping fits the real data best.

Candidate mappings are:

* **As-is mapping** - the value is copied without any transformation.
* **Heuristic mapping** - a predefined transformation rule (for example, a case or format change) that fits the sampled data.
* **AI-generated script mapping** - a MEL script generated by the Smart Integration microservice from sample value pairs.
* **Categorical mapping** - a MEL script generated by the microservice that maps a set of application values to a fixed set of midPoint values (for example, a status code to a lifecycle state).
* **System mapping** - a predefined mapping for well-known schemas such as LDAP, Active Directory or SCIM.

midPoint validates every candidate against sample data, assigns it an *expected quality* and chooses the candidate with the highest quality.

The result is a `MappingsSuggestionType` structure, which contains:

* `attributeMappings` - list of recommended attribute mappings (`AttributeMappingsSuggestionType`), each with a resource attribute definition containing either inbound or outbound mapping and its expected quality.
* `iterationSpecification` - an optional default iteration specification, added when a recommended script uses iteration variables.

The recommendations are not applied to the resource automatically.
They are stored in the work state of the recommendation task, and the user can review and accept them in the GUI.

=== Execution

The operation runs as a background task which is submitted by `SmartIntegrationService.submitSuggestMappingsOperation()`.
The activity has three child activities that run in this order:

. `statisticsComputation` - computes object type statistics for the resource object type, or reuses the latest existing statistics.
The step is skipped if the `RAW_DATA_ACCESS` permission is not granted.
. `schemaMatching` - computes the schema match (attribute pairs) and stores it as a smart integration artifact, see xref:../../schema-match.adoc[Schema Match].
The match is AI-assisted only if the `SCHEMA_ACCESS` permission is granted.
If `SCHEMA_ACCESS` is granted and a recomputation is not forced, the latest existing (non-expired) schema match is reused instead of being computed again.
Without `SCHEMA_ACCESS`, the schema match is always computed anew.
. `mappingsSuggestion` - runs the mapping recommendation itself (`MappingsSuggestionOperation`) and stores the result in the task work state.

Before the operation runs, midPoint checks the `#smartIntegration` authorization, see xref:../../security/authorization.adoc[].

== Inputs

The operation takes these inputs:

[cols="25%,15%,60%",options="header"]
|===
| Input | Required | Description

| Resource and object type
| yes
| The resource OID and the object type identification (kind and intent) for which mappings are recommended.

| Schema match
| yes
a| `SchemaMatchResultType` produced by the `schemaMatching` step.
It contains a list of matched pairs (`SchemaMatchOneResultType`), and each pair has:

* `shadowAttributePath` and `focusPropertyPath` - the paths of the matched items,
* `shadowAttribute` and `focusProperty` - the item definitions that are sent to the microservice,
* `isSystemProvided` - whether the pair comes from a well-known schema built into midPoint or from the AI service. See <<Well-Known Schemas>>.

| Direction (`inbound`)
| yes
| `true` recommends inbound mappings (shadow attribute -> focus property).
`false` recommends outbound mappings (focus property -> shadow attribute).
See <<Mapping Direction>>.

| Target paths to ignore (`targetPathsToIgnore`)
| no
| Target paths that should get no new recommendations, for example targets of recommendations the user has already accepted.
(Target paths of mappings already configured on the object type are also always excluded, even if they are not listed here.)

| Data access permissions (`permissions`)
| no
a| `DataAccessPermissionType` values granted to the task:

* `RAW_DATA_ACCESS` - allows sending sample attribute values to the AI microservice (AI-generated and categorical mappings).
Without it, only as-is, heuristic and system mappings are evaluated.
* `SCHEMA_ACCESS` - allows the AI-assisted schema matching in the `schemaMatching` step.

| Object type statistics
| no
| `ObjectSetStatisticsType` computed by the `statisticsComputation` step (available only with `RAW_DATA_ACCESS`).
It is used to detect attributes whose values are mostly missing and to get value distributions for categorical mappings.

| Force schema match recomputation (`forceRecomputeSchemaMatch`)
| no
| If `true`, the schema match is computed again even if a valid (non-expired) one already exists for the resource object type.
The GUI sets it when the user explicitly asks to regenerate the recommendations.
If `false` (default), an existing schema match is reused when `SCHEMA_ACCESS` is granted, for example one computed earlier for correlation recommendations.

| Retry count
| no
| The number of times midPoint asks the microservice again when a generated script fails validation.
It is read from `mappingSuggestionRetryCount` in the `<smartIntegration>` system configuration and defaults to `1`.
See <<Retry of AI-Generated Scripts>>.
|===

The operation also uses sample shadows that have owners, collected at runtime.
The number of samples is limited by the shadow sampling settings, see xref:../../shadow-sampling.adoc[].

== Well-Known Schemas

A *well-known schema* is a widely used resource schema that midPoint recognizes out of the box.
For these schemas, Evolveum engineers have prepared schema matches and mappings in advance, so midPoint does not need to rely only on AI for them.

These well-known schemas are supported:

[cols="35%,65%",options="header"]
|===
| Schema type | Description

| `SCIM_2_0_USER` | SCIM 2.0 User (RFC 7643 User Schema)
| `LDAP_INETORGPERSON` | LDAP `inetOrgPerson` object class (RFC 2798)
| `LDAP_GROUP_OF_NAMES` | LDAP `groupOfNames` / `groupOfUniqueNames` object class
| `LDAP_ORGANIZATIONAL_UNIT` | LDAP `organizationalUnit` object class
| `AD_USER` | Active Directory user
| `AD_GROUP` | Active Directory group
| `AD_ORGANIZATIONAL_UNIT` | Active Directory organizational unit
|===

midPoint detects a well-known schema from the connector type of the resource and the object class of the object type.
The detection happens in the `schemaMatching` step, and the detected type is stored in `wellKnownSchemaType` of the schema match.

=== Well-Known Schema Match

If a well-known schema is detected, midPoint adds its predefined attribute pairs (shadow attribute -> focus property) to the schema match and marks them with `isSystemProvided = true`.
It does this even without the `SCHEMA_ACCESS` permission, because no data is sent to the AI service.

If AI-assisted schema matching is also used, AI pairs are added only when they are not already among the predefined pairs.
Predefined pairs therefore take precedence over AI pairs.

The operation evaluates predefined pairs in the same way as any other pair (see <<Mapping Strategy Evaluation>>), so these recommendations are still filtered by quality.

=== Well-Known Mappings

In addition to the schema match, every well-known schema has a set of predefined *well-known mappings* (also called *system mappings*), prepared by Evolveum engineers.
There are separate sets for inbound and outbound direction.
A well-known mapping can be an as-is mapping or a mapping with a predefined script, for example a group name prefixed with the resource name (`<resource>:<cn>`).

Well-known mappings are curated domain knowledge, not AI guesses.
This is why they are handled differently from other candidates:

* They are *always recommended* when the schema is detected, regardless of their quality.
The quality thresholds that apply to other candidates do not apply to them.
* If sample data is available, midPoint still computes their expected quality against the validation samples.
The quality is stored in `expectedQuality`, but it is never used to discard the mapping.
* They are marked with `SYSTEM` provenance metadata, so the GUI can tell them apart from AI recommendations.
* Like all other recommendations, they are skipped if their target already has a mapping.

== Mapping Direction

The operation recommends mappings in only one direction per run, set by the `inbound` input.
Both directions use the same schema match pairs.
The direction decides which side of a pair is the source and which is the target, and this affects the whole evaluation: sampling, quality assessment, the variable name used in scripts and the shape of the resulting mapping.

[cols="22%,39%,39%",options="header"]
|===
| Aspect | Inbound | Outbound

| Data flow
| shadow attribute -> focus property
| focus property -> shadow attribute

| Source / target values
| shadow values / focus values
| focus values / shadow values

| Input variable in scripts
| `input`
| local name of the focus property (e.g. `givenName`)

| Existing mappings excluded by
| focus target path of existing inbound mappings
| resource attributes that already have an outbound mapping

| Read-only attributes
| evaluated
| skipped

| Categorical mappings
| supported
| not supported

| Mapping name
| `<attribute>-into-<focusPath>`
| `<focusPath>-to-<attribute>`

| Default range (`target/set/predefined`)
| `matchingProvenance` for multivalued focus items, `all` otherwise
| `all`
|===

All mappings created by the operation have `strong` strength.
Well-known mappings are the only exception, because their strength is defined by the well-known schema provider.

=== Inbound

Inbound mappings bring data from the resource into midPoint.
The shadow attribute is the source and the focus property is the target.
Inbound is the typical direction when a resource is connected as an authoritative source, for example an HR system.

Specifics of the inbound direction:

* In the recommended scripts, the shadow attribute value is always available as the `input` variable, not under the attribute name.
For example, a script for the `mail` attribute uses `input`, not `mail`.
* If the focus item is multivalued, the mapping range is `matchingProvenance` (see xref:/midpoint/reference/expressions/mappings/range/[Mapping Range]).
This way the mapping manages only the values it created itself and does not remove values that come from other sources.
* Object type statistics are used only in this direction.
They help detect attributes whose values are mostly missing on the resource, and they provide value distributions for categorical mappings (see <<Categorical Mappings>>).

=== Outbound

Outbound mappings send data from midPoint to the resource.
The focus property is the source and the shadow attribute is the target.
Outbound is the typical direction when midPoint provisions accounts to a target system.

Specifics of the outbound direction:

* In the recommended scripts, the focus property value is available under the local name of the focus property, not as `input`.
For example, a script whose source is `givenName` uses the variable `givenName`.
* Attributes that cannot be modified on the resource are skipped, because an outbound mapping for them would make no sense.
* Categorical mappings are not recommended.
* Outbound well-known mappings may depend on the sample shadows, for example to build a distinguished name (DN) that follows the structure of existing accounts.

== Processing Flow

The `mappingsSuggestion` activity runs these steps in order:

. **Shadow sampling** - collect sample shadows together with their owners.
. **Exclusion of existing mappings** - determine which targets get no new recommendations.
. **Well-known mappings** - add predefined mappings if a well-known schema was detected.
. **Per-attribute evaluation** - find the best mapping for every schema match pair.
. **Selection of candidates** - filter, deduplicate and order all candidates.
. **Iteration specification** - add a default iteration specification if needed.

=== 1. Shadow Sampling

midPoint needs real data to validate candidate mappings, so it first collects sample shadows of the object type that have an *owner*.
The owner is the focus object linked to the shadow or, if the shadow is not linked yet, the focus object found by correlation.
Shadows without an owner are ignored, because they provide no value to compare with.

Each sample entry is a pair of a shadow and its owner.
The samples are split into two disjoint sets:

* **LLM samples** - a small set that is sent to the AI microservice as examples when a script is generated.
* **Validation samples** - a larger set used to compute the expected quality of every candidate.

The size of both sets depends on whether shadow caching is enabled, see xref:../../shadow-sampling.adoc[].

=== 2. Exclusion of Existing Mappings

midPoint recommends no mapping for a target that is already covered.
The excluded target paths are the union of:

* targets of mappings already configured on the object type: focus target paths of inbound mappings, or resource attributes that have an outbound mapping,
* targets of recommendations the user has already accepted.

The exclusion is based on the target path only, regardless of the source or the expression.
It applies to all candidates created in the following steps.

=== 3. System (Well-Known Schema) Mappings

If the schema match contains a detected `wellKnownSchemaType`, midPoint takes the predefined well-known mappings for that schema in the current direction.
If validation samples are available, it computes the expected quality of each of them.
All of them are then added to the candidates without any quality filtering.
See <<Well-Known Mappings>> for details.

=== 4. Per-Attribute Mapping Evaluation

Every pair from the schema match is evaluated independently, and the pairs are processed in parallel.
The security context of the task (authentication and connection information) is passed to the worker threads, so the evaluation runs under the same identity as the task.
Progress is reported in the `mappingsSuggestion` operation state, with one item per pair.

The following diagram gives an overview of how one pair is evaluated:

.Decision flow for one schema match pair
----
Schema match pair
    ↓
Outbound and attribute not modifiable? ──YES→ SKIP
    ↓ NO
Value pairs sampled? ──NO→ No-data handling (see below)
    ↓ YES
Source value in < 5 % of pairs? ──YES→ SKIP (missing source data)
    ↓ NO
Target value in < 5 % of pairs? ──YES→ Try categorical mapping (inbound + RAW_DATA_ACCESS)
    ↓ NO                                 or as-is without quality
All source values equal targets? ──YES→ As-is, quality 1.0
    ↓ NO
Any multivalued pair? ──YES→ As-is without quality
    ↓ NO
Pick the best of:
  - as-is (baseline quality)
  - best heuristic rule
  - AI script (RAW_DATA_ACCESS only, with retry)
    ↓
Quality < 0.1? ──YES→ SKIP (low quality)
    ↓ NO
Mapping recommendation (SUCCESS)
----

.No-data handling
----
Inbound and source attribute missing in > 95 % of objects (statistics)? ──YES→ SKIP
    ↓ NO
Inbound + RAW_DATA_ACCESS? ──YES→ Try categorical mapping
    ↓ NO
As-is without quality
----

In detail, midPoint goes through the following decision sequence for each pair.
The first rule that applies decides the result.

. **Read-only attribute** - in the outbound direction, attributes that cannot be modified on the resource are skipped.
. **Building value pairs** - to find out how the resource value relates to the midPoint value, midPoint puts them side by side for each sample of correlated object and its owner.
Such value pairs show what a mapping has to do, and they are also used to test whether a candidate mapping really turns one value into the other.
. **No value pairs** - if no value pairs could be collected (the LLM sample or the validation sample is empty):
** inbound, with object type statistics: if the attribute has no value in more than 95 % of the resource objects, the pair is skipped (missing source data),
** inbound, with `RAW_DATA_ACCESS`: a <<Categorical Mappings,categorical mapping>> is tried,
** otherwise an as-is mapping without expected quality is recommended.
. **Missing source data** - if fewer than 5 % of the validation pairs have a source value, the pair is skipped.
. **Missing target data** - if fewer than 5 % of the validation pairs have a target value (for example, before the initial import the focus property is still empty):
** inbound, with `RAW_DATA_ACCESS`: a categorical mapping is tried,
** otherwise an as-is mapping without expected quality is recommended.
. **As-is is sufficient** - if every source value equals its target value after type conversion, an as-is mapping with expected quality `1.0` is recommended.
. **Multivalued data** - if any value pair has more than one value on either side, an as-is mapping without expected quality is recommended.
. **Finding the best expression** - otherwise midPoint compares several candidates on the validation samples and keeps the one with the highest quality:
.. as-is mapping (the baseline),
.. the best matching <<Heuristic Mappings,heuristic rule>>,
.. with `RAW_DATA_ACCESS`, an <<AI-Generated Script Mappings,AI-generated script>> obtained with retries (see <<Retry of AI-Generated Scripts>>).

When a result is selected, midPoint checks it against the minimum quality.
If the expected quality is known and lower than `0.1`, the pair is skipped.
Otherwise midPoint builds the recommendation and marks its provenance (see <<Provenance>>):

* `SYSTEM` if the recommendation was made entirely without an LLM,
* `AI` if an LLM was used (either for the schema match pair or for the mapping script).

==== Retry of AI-Generated Scripts

A script generated by the AI microservice may not work.
For example, it can contain a syntax error, call a function that is not allowed, or fail on some input value.
midPoint therefore validates every generated script and gives the microservice a chance to fix it.

.Retry flow
----
Call SUGGEST_MAPPING (examples + errorLog + previousScript)
    ↓
Script empty, "input" or "null"? ──YES→ No AI candidate (as-is mapping)
    ↓ NO
Evaluate on validation samples ──OK→ AI candidate (quality compared with others)
    ↓ ERROR
Attempts left? ──YES→ Call again with errorLog + previousScript
    ↓ NO
FAILURE of the whole pair
----

The maximum number of attempts is `1 + mappingSuggestionRetryCount` (by default 2 attempts in total).
In every attempt:

. midPoint calls the `SUGGEST_MAPPING` microservice method.
The request contains the definitions of both attributes, the direction, and the LLM value pairs as examples.
From the second attempt on, it also contains:
** `previousScript` - the script returned in the previous attempt,
** `errorLog` - the error message from the previous attempt's validation, if there was one.
. If the response contains no script, or the script is just `input` or `null`, the AI does not propose any transformation, and no AI candidate is created.
. Otherwise the script is wrapped into a MEL expression and evaluated on the validation samples.
The evaluation uses a restricted expression profile for safe evaluation.
. Depending on the result:
** the script evaluates successfully - it becomes the AI candidate, and its quality is compared with the other candidates,
** the evaluation fails with an expression evaluation or security violation error, and attempts remain - the error message is stored as `errorLog` and the next attempt starts,
** the evaluation fails in the last attempt - the error is propagated and the whole pair ends with `FAILURE`,

Setting `mappingSuggestionRetryCount` to `0` disables retries, so only one attempt is made.

=== 5. Selection of Best Candidates

After all pairs are processed, midPoint has a pool of candidates from steps 3 and 4.
Before a candidate enters the pool:

* it is dropped if its target is excluded (see step 2),
* it is dropped if its expected quality is low,
* if the same mapping is already in the pool (the same source, target and script, where the script is empty for as-is mappings), only one of them is kept.
A `SYSTEM` mapping replaces an `AI` one; otherwise the mapping that is already in the pool is kept.

Well-known mappings from step 3 are subject only to the first check (excluded targets).
They skip the quality threshold and deduplication.

The same target can get more than one recommendation if the recommendations differ in source or script, for example a well-known mapping and an AI mapping for the same focus property.
The final list is grouped by target path and, within each target, ordered by expected quality from highest to lowest.
Recommendations without expected quality come last.

=== 6. Iteration Specification

Some recommended scripts may use the iteration variables `iterationToken`, `iteration` or `attempt`, for example when a DN is composed as `cn=<fullName + iterationToken>,...`.
These variables work only if the object type has an iteration specification.
So if any recommended script uses one of them, midPoint adds an `iterationSpecification` to the result:

* if the object type already has an iteration specification, a copy of it is used,
* otherwise a default specification is added: start `1`, end `10`, and `useTokenOnlyOnConflict` set to `true`.
With this default, the token is used only when the first value conflicts with an existing one.

== Mapping Strategy Evaluation

This section describes the individual kinds of candidate mappings.
The order in which they are tried is described in <<4. Per-Attribute Mapping Evaluation>>.

=== Missing or Insufficient Data

A mapping can only be validated if there is data on both sides.
midPoint distinguishes three situations:

* **No value pairs at all** - no sampled object with an owner has a value for this pair.
This typically happens for a new resource that has no correlated accounts yet.
midPoint cannot validate anything, so it recommends an as-is mapping without expected quality (or a categorical mapping, see below).
For inbound mappings, it first checks the object type statistics: if the attribute is empty in more than 95 % of all resource objects, no mapping is recommended, because there is almost nothing to map.
* **Missing source data** - fewer than 5 % of the validation pairs have a source value.
A mapping from an almost always empty source would be useless, so no mapping is recommended.
* **Missing target data** - fewer than 5 % of the validation pairs have a target value.
This is typical before the initial import, when the focus property has not been populated yet.
midPoint cannot compute the quality, so it recommends an as-is mapping without expected quality (or a categorical mapping).

=== As-Is Mapping

An as-is mapping copies the source value to the target without any expression.
It is the simplest candidate and also the baseline for all other candidates.

midPoint recommends an as-is mapping in these cases:

* every validation source value equals its target value after conversion to the target type - expected quality `1.0`,
* there is not enough data to validate anything (see above) - no expected quality,
* the values are multivalued - no expected quality,
* neither a heuristic rule nor an AI script beats the as-is quality - the as-is quality is used.

=== Heuristic Mappings

Heuristic rules are simple, predefined transformations that cover the most common differences between the resource and midPoint values.
They are evaluated locally, without the AI microservice, so they are available even without `RAW_DATA_ACCESS`.

The available rules are:

[cols="40%,60%",options="header"]
|===
| Rule | Transformation

| `trim` | Remove leading and trailing whitespace
| `toLowerCase` | Convert to lowercase
| `toUpperCase` | Convert to uppercase
| `stripDiacritics` | Strip diacritical marks (e.g. `Müller` -> `Muller`)
| `trimAndLowerCase` | Trim and convert to lowercase
| `trimAndUpperCase` | Trim and convert to uppercase
| `trimAndStripDiacritics` | Trim and strip diacritical marks
| `lowerCaseAndStripDiacritics` | Convert to lowercase and strip diacritical marks
| `upperCaseAndStripDiacritics` | Convert to uppercase and strip diacritical marks
| `trimLowerCaseAndStripDiacritics` | Trim, convert to lowercase and strip diacritical marks
| `trimUpperCaseAndStripDiacritics` | Trim, convert to uppercase and strip diacritical marks
|===

Each rule is tried only if it can make a difference for the sampled data.
For example, `toLowerCase` is tried only if some source value contains an uppercase letter.
Applicable rules are evaluated on the validation samples, simpler rules first.
The rule with the highest quality wins; if two rules have the same quality, the simpler one is kept.
The winning rule is used only if its quality is higher than the as-is quality.

=== AI-Generated Script Mappings

If no simple transformation fits, midPoint asks the AI microservice to write a script.
This requires the `RAW_DATA_ACCESS` permission, because sample values are sent to the microservice.

midPoint calls the `SUGGEST_MAPPING` method with:

* the definitions of the resource attribute and the focus property,
* the mapping direction,
* the LLM value pairs as examples of the expected transformation.

The microservice returns a MEL script and its description.
midPoint evaluates the script on the validation samples and computes its quality.
The script is used only if its quality is higher than the quality of the as-is mapping and the best heuristic rule.

If the script fails, midPoint asks the microservice to fix it, see <<Retry of AI-Generated Scripts>>.

=== Categorical Mappings

Some focus properties accept only a fixed set of values, for example `lifecycleState` (`draft`, `proposed`, `active`, `suspended`, ...) or properties with an enumeration type such as an activation status.
Resource attributes often express the same information with their own codes, for example `A`, `T` or `Terminated`.
A categorical mapping translates each resource value to one of the allowed midPoint values.

Categorical mappings are used when there is not enough paired data to learn the transformation from examples, that is when there are no value pairs or the target data is missing.
They are tried only if all of these conditions are met:

* the direction is inbound,
* `RAW_DATA_ACCESS` is granted and object type statistics are available,
* the focus property is `lifecycleState` or has an enumeration type,
* the statistics contain the value distribution of the resource attribute.

midPoint calls the `SUGGEST_CATEGORICAL_MAPPING` method with the attribute definitions, the distinct resource values from the statistics, and the allowed midPoint values.
The microservice returns a MEL script that maps one to the other.

Because there are no paired values, the quality of the script cannot be computed.
midPoint only checks that the script runs without an error on one of the resource values.
If it does, the categorical mapping is recommended without expected quality.
If it does not, an as-is mapping without expected quality is recommended instead.

== Quality Assessment

The *expected quality* is the share of validation samples for which the mapping produces exactly the target value.
It is a number from `0.0` to `1.0`, rounded to two decimal places.

midPoint computes it as follows:

. Only value pairs with exactly one value on each side are compared.
Multivalued and empty pairs are ignored.
. The mapping expression is applied to the source value.
For as-is mappings, the source value is used directly.
. The result is compared with the target value as text.
. The quality is the number of matching pairs divided by the number of compared pairs.

Recommendations created without validation (see <<As-Is Mapping>> and <<Categorical Mappings>>) have no expected quality.

Well-known mappings are never dropped because of their quality.

== Result Structure

The result (`MappingsSuggestionType`) contains a list of `attributeMappings` and an optional `iterationSpecification` (see <<6. Iteration Specification>>).

Each item of `attributeMappings` (`AttributeMappingsSuggestionType`) contains:

* `definition` - a resource attribute definition (`ResourceAttributeDefinitionType`) with:
** `ref` - the resource attribute,
** either one `inbound` or one `outbound` mapping, depending on the direction (see <<Mapping Direction>> for the name, strength and range),
** `expression` inside the mapping - a MEL script with its description, or no expression for as-is mappings.
* `expectedQuality` - the expected quality, if it could be computed (see <<Quality Assessment>>).

The definition has the same format as attribute definitions in the schema handling of a resource, so it can be added to the object type as it is.

.Example of a recommended inbound mapping (heuristic rule `toLowerCase`)
[source,xml]
----
<attributeMappings>
    <definition>
        <ref>ri:mail</ref>
        <inbound>
            <name>mail-into-emailAddress</name>
            <strength>strong</strength>
            <expression>
                <description>Convert to lowercase</description>
                <script>
                    <language>mel</language>
                    <code>input.lc()</code>
                </script>
            </expression>
            <target>
                <path>emailAddress</path>
                <set>
                    <predefined>all</predefined>
                </set>
            </target>
        </inbound>
    </definition>
    <expectedQuality>0.97</expectedQuality>
</attributeMappings>
----

=== Provenance

Every recommendation is marked with provenance metadata, so the GUI can show where the recommendation comes from.
The provenance is stored as value metadata of the recommendation:

[cols="15%,45%,40%",options="header"]
|===
| Provenance | Origin | Meaning

| `AI`
| Artificial intelligence
| An LLM was used to create the recommendation, either for the schema match or for the mapping script.

| `SYSTEM`
| System intelligence
| The recommendation was created entirely without an LLM, from a well-known schema match or a well-known mapping.
|===

== Limitations

* **Simple attributes only.** Mappings are recommended only for simple resource attributes.
Activation, credentials and associations are not supported.
* **One source, one target.** Every recommendation maps exactly one resource attribute to exactly one focus property.
Mappings that combine several sources (for example, a full name from given and family name) are not recommended.
* **Multivalued attributes.** No transformation is recommended for multivalued values, only an as-is mapping without expected quality.
* **Fixed heuristics.** Heuristic rules cover only whitespace trimming, letter case and diacritics.
* **Categorical mappings are inbound only** and their quality is never computed.
* **Well-known schemas** are detected only for the schema types listed in <<Well-Known Schemas>>.
