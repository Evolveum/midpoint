= Smart object types recommendation
:page-toc: top
:page-since: "4.11.0"
:page-upkeep-status: green

== Overview

The *smart object types recommendation* operation proposes resource object types for a single object class of a resource.
It is usually the first recommendation the user runs when a new resource is connected, because all other recommendations (correlation, mappings, associations) work on object types.

One object class often contains objects with different meaning, for example regular employees, contractors and service accounts.
The operation analyzes statistics of the real data in the object class and proposes how to split it into object types.
For each object type, it proposes:

* **kind and intent** - the identification of the object type, for example `account/employee`,
* **display name and description** - a human-readable name and an explanation of the object type,
* **delineation** - which objects of the object class belong to the object type, expressed by filters and optionally a base context,
* **focus type** - the midPoint type (for example `UserType` or `RoleType`) that the objects correspond to, see <<5. Focus type recommendation>>.

The recommendations are generated by the Smart Integration microservice.
There are no system (non-AI) object type recommendations.

The result is an `ObjectTypesSuggestionType` structure with a list of resource object type definitions (`ResourceObjectTypeDefinitionType`).
The recommendations are not applied to the resource automatically.
They are stored in the work state of the recommendation task, and the user can review and accept them in the GUI.

=== Execution

The operation runs as a background task which is submitted by `SmartIntegrationService.submitSuggestObjectTypesOperation()`.
The activity has three child activities that run in this order:

. `statisticsComputation` - provides object class statistics, see <<Object class statistics>>.
The step is skipped if the `STATISTICS_ACCESS` permission is not granted.
. `objectTypesSuggestion` - runs the object types recommendation itself (`ObjectTypesSuggestionOperation`) and stores the result in the task work state.
No result is produced without `STATISTICS_ACCESS`.
. `focusTypeSuggestion` - recommends a focus type for every recommended object type and updates the result in the work state.
The step is skipped if the `SCHEMA_ACCESS` permission is not granted.
At the end, it submits the schema match preload task, see <<Schema match preloading>>.

Before the operation runs, midPoint checks the `#smartIntegration` authorization, see xref:../../security/authorization.adoc[].

== Object class statistics

The microservice does not get the resource objects themselves.
It gets aggregated statistics of the object class: for each attribute, for example, how many objects miss a value, which values are the most frequent, and which value patterns occur (such as DN suffixes).
See xref:../../statistics.adoc[Statistics] for details.

The `statisticsComputation` step gets the statistics in this order:

. Latest stored statistics of the object class are reused, if they have not expired.
Statistics expire after the time configured in `statisticsTtl` (default `P1D`).
. Otherwise, the step goes through all objects of the object class, computes new statistics and stores them as a `SmartIntegrationArtifactType` object.

Before the statistics are sent to the microservice, they are trimmed to keep the request small and to leave out values that carry little information:

[cols="40%,60%",options="header"]
|===
| Statistics item | Trimming

| Value counts
| Only the 10 most frequent values of each attribute are kept.
If no value of the attribute occurs at least twice, all value counts of the attribute are removed.

| DN suffix patterns
| Only the 20 most frequent patterns of each attribute are kept.

| First token and last token patterns
| Only the 10 most frequent patterns of each type and attribute are kept.

| Attributes
| Attributes that have no value in any object, or that have no value counts and no patterns left after trimming, are removed.
|===

The common midPoint namespace prefix (`c:`) is removed from item paths in the request, see xref:../../service-item-paths.adoc[].

== Processing flow

The `objectTypesSuggestion` and `focusTypeSuggestion` activities run these steps:

.Object types recommendation flow
----
Object class schema + trimmed statistics
    ↓
Call SUGGEST_OBJECT_TYPES (+ validation feedback, regenerate mode, previous object types)
    ↓
Test every filter and base context on the resource
    ↓
All valid? ──YES→ Build result
    ↓ NO
First attempt? ──YES→ Call again with validation feedback
    ↓ NO
Build result from the second response, invalid filters marked as invalid
    ↓
Skip duplicates and object types already defined on the resource
    ↓
SCHEMA_ACCESS granted? ──YES→ Recommend focus type for each object type
    ↓
ObjectTypesSuggestionType
----

=== 1. Request to the microservice

midPoint calls the `SUGGEST_OBJECT_TYPES` method of the microservice.
The request contains:

* **Object class schema** - the name and description of the object class and, for every attribute, its name, type, description and cardinality.
If the resource supports them, the password and the activation items (administrative status, valid from, valid to) are added too.
* **Statistics** - the trimmed object class statistics, see <<Object class statistics>>.
* **Validation feedback** - only in the second attempt, see <<3. Retry with validation feedback>>.
* **Regenerate mode and previous object types** - only if they are set, see <<Regeneration>>.

The microservice returns a list of object types.
Each of them has a kind, an intent, a display name, a description, delineation filters written in xref:../../../concepts/query/midpoint-query-language/index.adoc[midPoint Query Language], and optionally a base context (an object class and a filter).

=== 2. Validation of delineation filters

A filter generated by an LLM may refer to an attribute that does not exist, use a wrong syntax, or use an operation that the resource does not support.
midPoint therefore checks every filter in two steps before it is recommended:

. *Schema check.* The filter arrives as plain text in midPoint Query Language, for example `attributes/ri:employeeType = "internal"`.
midPoint parses the text and looks up every referenced attribute in the object class definition from the resource schema.
This step reports an error if the filter uses an attribute that the object class does not have, a value of a wrong type, or invalid syntax.
. *Resource check.* midPoint runs the filter on the resource as a search that returns at most one object.
Even a filter that is valid according to the schema may still fail here, e.g. when the connector does not support the used operation.

The base context is checked in the same way: its filter must pass both the schema check (against the base context object class) and the resource check.
The base context object class must exist in the resource schema, and both the object class and the filter must be set.

=== 3. Retry with validation feedback

If any filter or base context of any object type fails validation, midPoint gives the microservice a chance to fix it:

. midPoint builds *validation feedback*: for every object type from the response, it sends back the object type as it was proposed, together with the error messages of its filters and base context.
. midPoint calls `SUGGEST_OBJECT_TYPES` again with the same inputs and the validation feedback.
. The new response is validated again.

At most two attempts are made.
If the second response still contains invalid filters, midPoint does not discard it.
It uses the second response as it is and marks every invalid filter and base context as invalid, including the error message (see <<Provenance and validation markers>>).
The user can then fix or discard such object types in the GUI.

=== 4. Building the result

midPoint converts every object type from the response into a resource object type definition.
Some object types are skipped:

* **Object types already defined on the resource.**
If the schema handling of the resource already contains an object type with the same object class, the same filters (in any order) and the same base context, the recommendation is skipped.
This covers both object types created manually and recommendations that the user has already accepted.
* **Duplicate kind and intent.**
If the response contains several object types with the same kind and intent, only the first one is kept.

=== 5. Focus type recommendation

If `SCHEMA_ACCESS` is granted, the `focusTypeSuggestion` activity recommends a focus type for every recommended object type.

If the focus type cannot be determined for an object type, the error is logged and the object type stays without a focus type.
The other object types are not affected.

The same operation is also available separately for existing object types, see xref:../focus-type/focus-type-recommendation.adoc[Smart focus type recommendation].

== Regeneration

If the user is not satisfied with the recommended object types, the recommendation can be generated again.
The user can say what was wrong, and midPoint passes this to the microservice as the regenerate mode, together with the object types from the previous recommendation:

[cols="25%,75%",options="header"]
|===
| Regenerate mode | Meaning

| `NEW_DATA_SPLIT`
| The split of the objects into object types is wrong.
The microservice should group the objects in a different way.

| `NEW_FILTER`
| The split of the objects into object types is correct, but the filters (classification criteria) are wrong.
The microservice should keep the object types and propose different filters.
|===

If no regenerate mode is set, the recommendation is generated from scratch.

== Result structure

The result (`ObjectTypesSuggestionType`) contains a list of `objectType` items.
Each of them is a resource object type definition (`ResourceObjectTypeDefinitionType`) with:

* `kind` and `intent`,
* `displayName` and `description`,
* `delineation` with `objectClass`, `filter` (one or more) and optionally `baseContext`,
* `focus type` - the recommended focus type, if it was recommended.

The definition has the same format as object type definitions in the schema handling of a resource, so it can be added to the resource as it is.

.Example of a recommended object type
[source,xml]
----
<objectType>
    <kind>account</kind>
    <intent>employee</intent>
    <displayName>Employee</displayName>
    <description>Accounts of regular employees.</description>
    <delineation>
        <objectClass>ri:inetOrgPerson</objectClass>
        <filter>
            <q:text>attributes/ri:employeeType = "employee"</q:text>
        </filter>
        <baseContext>
            <objectClass>ri:organizationalUnit</objectClass>
            <filter>
                <q:text>attributes/ri:dn = "ou=people,dc=example,dc=com"</q:text>
            </filter>
        </baseContext>
    </delineation>
    <focus>
        <type>UserType</type>
    </focus>
</objectType>
----

=== Provenance and validation markers

All recommended items are marked with `AI` provenance metadata, so the GUI can show that they come from the AI microservice:
`kind`, `intent`, `displayName`, `description`, delineation `filter`, `baseContext` (its `objectClass` and `filter`), and `focus type`.

Filters and base contexts that failed validation after the retry are additionally marked as *invalid*, together with the error message.

== Limitations

* **AI only.** Object types are recommended only by the AI microservice and only with `STATISTICS_ACCESS`.
There is no system (non-AI) fallback.
* **One object class per run.** Every run works on one object class.
Object types spanning several object classes are not recommended.
* **Statistics, not objects.** The microservice sees only aggregated and trimmed statistics.
Values that are not among the most frequent ones, or that do not repeat at all, are not visible to it.
* **One retry.** Invalid filters are corrected at most once.
Filters that are still invalid after the retry are recommended and marked as invalid.
* **Exact match of existing object types.** An existing object type is recognized only if its filters are textually identical to the recommended ones.
Equivalent filters written differently are not recognized.
