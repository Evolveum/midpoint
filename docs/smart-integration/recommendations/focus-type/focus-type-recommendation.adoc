= Smart focus type recommendation
:page-toc: top
:page-since: "4.11"
:page-upkeep-status: green

== Overview

The *smart focus type recommendation* operation proposes a focus type for a resource object type.
The focus type is the midPoint type of objects (for example `UserType`, `RoleType` or `OrgType`) that the resource objects of the object type correspond to.
It is stored in the `focus/type` item of the object type definition, and other recommendations (correlation, mappings) depend on it.

The recommendation is generated by the Smart Integration microservice from the schema of the object class and the identification of the object type.
There is no system (non-AI) focus type recommendation.

The result is a `FocusTypeSuggestionType` structure with a single focus type name.
The recommendation is not applied to the resource automatically: the user reviews and accepts it in the GUI.

=== Execution

The operation can be run in three ways:

[cols="30%,70%",options="header"]
|===
| Way | Description

| Background task
| Submitted by `SmartIntegrationService.submitSuggestFocusTypeOperation()` for an existing object type.
The `focusTypeSuggestion` activity runs the recommendation (`FocusTypeSuggestionOperation`) and stores the result in the task work state.
Without `SCHEMA_ACCESS`, the activity ends without a result.

| Synchronous call
| `SmartIntegrationService.suggestFocusType()` runs the recommendation directly and returns the result.
It is used by the GUI when the user asks for a focus type recommendation in the object type configuration, and also for object types that are not yet saved on the resource.

| Part of object types recommendation
| The `focusTypeSuggestion` child activity of the object types recommendation recommends a focus type for every recommended object type, see xref:../object-types/object-types-recommendation.adoc#_5_focus_type_recommendation[Focus type recommendation].
|===

Before the operation runs, midPoint checks the `#smartIntegration` authorization, see xref:../../security/authorization.adoc[].

== Inputs

The operation takes these inputs:

[cols="25%,15%,60%",options="header"]
|===
| Input | Required | Description

| Resource and object type
| yes
| The resource OID and either the kind and intent of an existing object type, or an object type definition (`ResourceObjectTypeDefinitionType`) that is not yet saved on the resource.
The object type definition must contain a delineation with an object class.

| Data access permissions
| yes
a| `DataAccessPermissionType` values granted to the operation:

* `SCHEMA_ACCESS` - allows sending the object class schema to the AI microservice.
Without it, the operation fails with an insufficient permissions error.
|===

== Processing flow

.Focus type recommendation flow
----
SCHEMA_ACCESS granted? ──NO→ Insufficient permissions error
    ↓ YES
Object class schema + kind and intent
    ↓
Call SUGGEST_FOCUS_TYPE
    ↓
FocusTypeSuggestionType (marked as AI-provided)
----

=== 1. Request to the microservice

MidPoint calls the `SUGGEST_FOCUS_TYPE` method of the microservice.
The request contains:

* **Kind and intent** - the identification of the object type, for example `account` and `employee`.
* **Object class schema** - the name and description of the object class and, for every attribute, its name, type, description and cardinality.
If the resource supports them, the password and the activation items (administrative status, valid from, valid to) are added too.
This is the same schema as in the object types recommendation.
* **Base context filter** - the filter of the base context of the object type, in midPoint Query Language, if the object type has one.

No resource objects or statistics are sent.
The only values in the request are those written in the base context filter, for example the DN of an organizational unit.
The common midPoint namespace prefix (`c:`) is removed from item paths in the request, see xref:../../service-item-paths.adoc[].

=== 2. Response

The microservice returns the name of the focus type, for example `UserType`.
MidPoint uses the returned name as it is and marks it with `AI` provenance metadata.

== Result structure

The result (`FocusTypeSuggestionType`) contains:

* `focusType` - the qualified name of the recommended focus type.

.Example of a recommended focus type
[source,xml]
----
<focusTypeSuggestion>
    <focusType>UserType</focusType>
</focusTypeSuggestion>
----

The example omits the provenance metadata (`_metadata`) that marks the `focusType` as AI-provided.

When the user accepts the recommendation, the focus type is set in the object type definition:

[source,xml]
----
<objectType>
    <kind>account</kind>
    <intent>employee</intent>
    ...
    <focus>
        <type>UserType</type>
    </focus>
</objectType>
----

== Configuration

The operation is affected by these settings in the `<smartIntegration>` container of the system configuration:

[cols="35%,15%,50%",options="header"]
|===
| Setting | Default | Description

| `serviceUrl`
| -
| URL of the Smart Integration microservice.

| `serviceApiKey`
| -
| API key sent with every request to the microservice.

| `serviceResponseTimeout`
| 120 seconds
| Maximum time to wait for a response from the microservice.
|===

See also xref:../../configuration.adoc[Smart Integration configuration].

== Limitations

* **AI only.** The focus type is recommended only by the AI microservice and only with `SCHEMA_ACCESS`.
There is no system (non-AI) fallback.
* **One focus type.** Exactly one focus type is recommended, without alternatives or a confidence score.
* **No validation.** The returned focus type name is not checked against the midPoint schema before it is recommended.
