= Smart associations recommendation
:page-toc: top
:page-since: "4.11"
:page-upkeep-status: green
:page-description: Generate association suggestions in the GUI and learn how midPoint identifies possible associations and generates their configuration.
== Overview

An *association* describes a relationship between resource objects, such as an account's membership in an application group.
For example, membership in the application's `invoice-approvers` group can be represented by an assignment to the `Invoice Approver` role in midPoint.

Configuring this manually means choosing the participating account and group types, connecting them through a membership reference, and defining *mappings* to translate between group membership and role assignments.
For importing membership, you also need *correlation* to find existing assignments and *synchronization* to decide whether to add or update them.
These settings have to work together.

*Association suggestions* prepare this configuration from your resource schema and configured object types.
Each suggestion includes the participants and membership reference, along with mappings from the application into midPoint (*inbound*) and from midPoint to the application (*outbound*).
It also includes assignment correlation and synchronization rules for inbound processing.
You review the suggestion, keep the directions you need, and save the settings to the resource.
Generating suggestions does not apply configuration or change memberships.

Association suggestions are generated by a predefined algorithm implemented in midPoint.

The algorithm does not use artificial intelligence (AI) or large language models (LLMs).
No membership data is sent to an external AI service.

== Key Concepts

Accounts and groups exist in the connected application.
An account represents a user there.
A group is an *entitlement*, a resource object representing access.
The account and group have different roles in the association:

[cols="20%,45%,35%",options="header"]
|===
| Term | Meaning | Example

| Subject | The resource object whose association is being processed. | The account whose membership is managed.
| Object | The resource object referenced by the association. | The `invoice-approvers` group.
| Shadow | MidPoint's record of a resource object. | The shadow representing the application group.
| Owner | The midPoint object linked to that shadow. | The `Invoice Approver` role linked to the group shadow.
|===

The group and role are separate objects: the group provides access in the application, while the role represents that access in midPoint.
The generated mappings use their link to translate between the two.
An account is similarly linked to its user.
See xref:../../../resources/entitlements/index.adoc[Entitlements and Associations] for the broader model.

== Prerequisites

Generation takes one resource and considers all its configured object types.
For account-to-group membership, prepare the following:

[cols="30%,70%",options="header"]
|===
| Requirement for generation | Why it is needed

| Resource connection and complete schema
| Supply the account and group definitions and the references between them.

| Configured account and entitlement types
| Define an account type and a group type for the association, for example `account/default` and `entitlement/app-group`.
Each type is identified by its kind and intent.
See xref:../../../resources/resource-configuration/schema-handling/object-types.adoc[Resource Object Types] for configuration details.

| Membership reference in the resource schema
| The resource schema must describe the membership relationship as a readable reference, such as `ri:group` between accounts and groups.
The suggestion uses this reference to prepare the association configuration.

| Smart Integration and resource permissions
| Allow generation and access to the resource.
Saving a suggestion also requires permission to edit the resource.
See xref:../../security/authorization.adoc[Smart Integration Authorization] for the required permissions.
|===

=== Before Processing Membership

Generation uses object type and reference definitions.
Membership processing also needs links between individual accounts and users, and between groups and roles.
Synchronization or provisioning normally creates these links.
If they already exist, the generated mappings reuse them.

[cols="30%,70%",options="header"]
|===
| Requirement for membership processing | Purpose

| Account linked to its user
| Inbound updates that user's assignments.
Outbound updates membership on the user's account.

| Group linked to its role
| Inbound uses the role as the assignment target.
Outbound uses the linked group as the membership target.

| Support and permissions for membership updates
| Allow outbound processing to change group membership in the application.
|===

== Generating Association Suggestions

Association suggestions can be generated from the resource configuration in the midPoint GUI.

=== Start Generation

. Open the resource for which you want to configure associations.
. Navigate to *Schema handling* → *Association types*.
. Turn on *Show suggestions*.
. Click *Generate suggestions*.
. Wait for the background task to finish.

After generation completes, the available association suggestions appear in the association types section.

=== Review Suggestions

Open the suggestions you want to review.
Check the subject and object types, the membership reference, and the generated mapping directions.

=== Apply Configuration

Save the reviewed association settings and resource changes for the suggestions you decide to use.

NOTE: Generating suggestions does not change existing memberships.
Memberships can change when the saved mappings are evaluated during synchronization, provisioning, or reconciliation.

== How Association Suggestions Work

The process uses configured object types and their references to identify possible
associations. It skips pairs that already have an association on the resource and
builds suggestions for the remaining combinations. The following sections explain
each step.

=== 1. Read the Resource Configuration

MidPoint first reads the resource schema and the configured object types, such as `account/default` and `entitlement/app-group`.
Together, these definitions describe the types of objects midPoint can work with and the references available between them.

=== 2. Find Possible Subjects

Every configured object type is considered as a subject.
For `account/default`, midPoint looks for references from accounts to other resource objects.
Each intent is considered separately.

Subjects can also be groups or other object types.
For example, a group-to-group suggestion can connect two objects of the same kind and intent.
This does not imply that a group refers to itself.

=== 3. Check Their References

For each subject type, midPoint examines its reference attributes.
Ordinary attributes are not considered.
A reference must pass all of these checks:

[cols="40%,60%",options="header"]
|===
| Requirement | Implementation check

| The reference is readable.
| `canRead()` must return `true`.

| The reference is not object-side.
| References whose `getParticipantRole()` is `OBJECT` are skipped.

| The native reference is not complex.
| `isComplexAttribute()` must return `false`.

| The target object class is not embedded.
| `isTargetingSingleEmbeddedObjectClass()` must return `false`.

| The generalized object-side class is not auxiliary.
| `isAuxiliary()` must return `false`.
|===

==== Example: LDAP Group Membership

A reference can point from an account to its groups even when LDAP stores membership on the groups.
The following example shows an account and a group that lists the account as a member:

.Account in LDAP
[source,text]
----
dn: uid=jnovak,ou=people,dc=example,dc=com
objectClass: inetOrgPerson
uid: jnovak
cn: Jan Novak
sn: Novak
----

.Group in LDAP
[source,text]
----
dn: cn=developers,ou=groups,dc=example,dc=com
objectClass: groupOfNames
cn: developers
member: uid=jnovak,ou=people,dc=example,dc=com
----

The account has no membership attribute in this example.
Instead, the group's `member` attribute contains the account's DN.
With suitable connector configuration, the resource schema can expose this relationship as an account-side reference, such as `ri:group`:

.From the account perspective
[source,text]
----
Account: jnovak
    |
    | ri:group
    v
Group: developers
----

Here, `ri:group` represents the account's membership in the group.
It does not require a physical `group` attribute on the LDAP account.
The group's `member` attribute alone is not enough for suggestions. The resource schema must expose a readable subject-side reference that passes the checks above.

==== How This Affects Association Suggestions

The generator uses reference definitions from the resource schema and the object types you have configured.
It does not read the individual accounts or groups shown above, or inspect their memberships.

For example, if `account/default` exposes an eligible `ri:group` reference whose target object class matches `entitlement/group`, the generator can prepare a suggestion connecting these types.
In the generated configuration, `ri:group` is the source reference, stored in `sourceAttributeRef`.
The logical association reference is named `group-group`, combining the source reference's local name (`group`) with the target type's intent (`group`).

Generating this suggestion does not verify that membership can be updated.
Applying membership changes later requires write support and sufficient permissions on the resource.

=== 4. Find Matching Object Types

A reference identifies a target *object class*, the schema definition describing the objects it points to.
MidPoint finds configured object types using that exact class name, including its namespace.
A reference with no matching type produces no candidate.

Several types may share the same class.
For example, `account/default` might expose `ri:group`, while three entitlement types use its target group class:

.Example candidate set
[cols="25%,35%,40%",options="header"]
|===
| Subject | Object (target) | Candidate relationship

| `account/default` | `entitlement/app-group` | Application group membership
| `account/default` | `entitlement/generic-group` | Generic group membership
| `account/default` | `entitlement/org-group` | Organizational group membership
|===

All three are candidates because their classes match, assuming none of the pairs is already configured.
The algorithm does not choose which category should grant access.

Rules called *delineation* distinguish which actual groups belong to each type.
Generation matches the class without evaluating those rules against group data.
Classification uses them when resource objects are processed.
See xref:../../../resources/resource-configuration/schema-handling/delineation.adoc[Object Type Delineation].

=== 5. Exclude Already Configured Associations

Before generating a suggestion, midPoint checks whether an association
between the same subject and object types already exists on the resource.

For example, consider three possible associations:

.Existing and potential associations
[source,text]
----
account/default
      |
      +----> entitlement/app-group      (already configured)
      |
      +----> entitlement/generic-group  (suggested)
      |
      +----> entitlement/org-group      (suggested)
----

MidPoint skips `entitlement/app-group` because its association
is already configured. The other two relationships remain eligible
for suggestions.

The comparison uses the *kind* and *intent* of both participants,
not the association's name. Renaming an existing association
does not make it eligible for another suggestion.

Only associations on the current resource are considered.
Associations configured on other resources do not affect generation.

NOTE: Association exclusion prevents duplicate configuration suggestions.

=== 6. Build the Suggested Configuration

For each remaining combination of subject type, reference, and target type,
midPoint generates an association definition.

For example, a suggestion connecting `account/default` to
`entitlement/app-group` through `ri:group` contains:

.Generated association suggestion
[source,text]
----
Subject: account/default
             |
             | ri:group
             v
Object: entitlement/app-group
             |
             v
Generated configuration:
    - Association name and display name
    - Subject and object types
    - Source reference (ri:group)
    - Inbound and outbound mappings
    - Membership correlation and synchronization
----

MidPoint identifies the participants by their kind and intent,
sets the source reference, and generates the mappings and rules
described in <<Generated Configuration>>.

When started from the GUI, generation runs as a background task.
The generated suggestions are then available for review.

If all supported associations are already configured or no
matching target types are found, the result may be empty.

== Generated Configuration

Each association suggestion includes mappings and rules for processing
membership between the resource and midPoint.

The following sections explain the generated configuration and how
it works after the suggestion is saved to the resource.

NOTE: The examples use illustrative names and references.
The actual configuration depends on the resource schema
and configured object types.

=== Mapping Direction

Inbound brings membership information into midPoint.
Outbound uses midPoint role assignments to manage membership in the application.

For example, suppose the LDAP `developers` group is linked to the `Developer` role in midPoint, and the user's LDAP account is linked to that user.

* *Inbound — LDAP to midPoint:* If the account belongs to `developers`, membership processing can assign the linked `Developer` role to the user.
* *Outbound — midPoint to LDAP:* Assigning the `Developer` role to the user can add their account to the `developers` group.

An *expression* is the part of a mapping that computes its result.
The outer expressions process the association, while the nested expressions supply the role or group reference.

[cols="24%,38%,38%",options="header"]
|===
| Aspect | Inbound: from the resource | Outbound: to the resource

| Purpose
| Represent application membership as role assignments.
| Provision membership from midPoint roles.

| Group-to-role link
| Finds the owner role of the referenced group shadow.
| Finds the group shadow linked to a relevant role.

| Outer expression
| `associationSynchronization`
| `associationConstruction`

| Nested expression
| `shadowOwnerReferenceSearch`
| `associationFromLink`

| Result
| An assignment targeting the role.
| An association value referencing the group.
|===

=== Outbound Mapping

Outbound processing uses the groups linked to the user's relevant roles to construct application membership.
Place this block under `associationType/subject/association`.

.Generated outbound mapping
[source,xml]
----
<outbound xmlns="http://midpoint.evolveum.com/xml/ns/public/common/common-3"
          xmlns:ri="http://midpoint.evolveum.com/xml/ns/public/resource/instance-3">
    <name>ACCOUNT-default-ref-ENTITLEMENT-app-group-outbound</name>
    <strength>strong</strength>
    <expression>
        <associationConstruction>
            <objectRef>
                <ref>ri:group</ref>
                <mapping>
                    <name>associationFromLink</name>
                    <strength>strong</strength>
                    <expression>
                        <associationFromLink/>
                    </expression>
                </mapping>
            </objectRef>
        </associationConstruction>
    </expression>
</outbound>
----

* `associationConstruction` builds the association value for each relevant role and evaluates the nested mapping for that role.
* `associationFromLink` supplies the reference to the role's linked group, such as `invoice-approvers` for `Invoice Approver`.
* `objectRef/ref` identifies the source reference, `ri:group`.
The connector uses the reference configuration to turn the association change into a membership update.

=== Inbound Mapping

Inbound processing finds the role representing an incoming group membership and prepares assignment data for that role.
For `invoice-approvers`, the role is `Invoice Approver`.
Place this block under `associationType/subject/association`.

This fragment shows the mapping part of the generated inbound configuration.
Complete it with the blocks in <<Membership Correlation>> and <<Membership Synchronization>> at the marked locations.

.Generated inbound mapping, with correlation and synchronization shown separately
[source,xml]
----
<inbound xmlns="http://midpoint.evolveum.com/xml/ns/public/common/common-3"
         xmlns:ri="http://midpoint.evolveum.com/xml/ns/public/resource/instance-3">
    <name>ACCOUNT-default-ref-ENTITLEMENT-app-group-inbound</name>
    <strength>strong</strength>
    <expression>
        <associationSynchronization>
            <objectRef>
                <ref>ri:group</ref>
                <mapping>
                    <name>shadowOwner-into-targetRef</name>
                    <strength>strong</strength>
                    <expression>
                        <shadowOwnerReferenceSearch/>
                    </expression>
                    <target>
                        <path>targetRef</path>
                    </target>
                </mapping>
            </objectRef>
            <!-- Insert the correlation block shown below here. -->
            <!-- Insert the synchronization block shown below here. -->
        </associationSynchronization>
    </expression>
</inbound>
----

* `shadowOwnerReferenceSearch` finds the owner of the group shadow.
For this account-to-group configuration, that owner is the role representing the group's access.
* `targetRef` is the assignment field identifying the role to assign.
The nested mapping, `shadowOwner-into-targetRef`, supplies its value.
* `associationSynchronization` uses the assignment data for correlation and synchronization.
This evaluator targets assignments.
Processing an association into a different item requires a different mapping design.

=== Membership Correlation

Correlation finds an existing assignment for the incoming membership.
Place this block under `inbound/expression/associationSynchronization`, after `objectRef`.

.Generated membership correlation
[source,xml]
----
<correlation xmlns="http://midpoint.evolveum.com/xml/ns/public/common/common-3">
    <correlators>
        <items>
            <name>membership-correlation</name>
            <description>Correlate group membership using existing assignments</description>
            <enabled>true</enabled>
            <item>
                <name>shadowOwner-into-targetRef</name>
                <ref>targetRef</ref>
            </item>
        </items>
    </correlators>
</correlation>
----

* `membership-correlation` names the items correlator, which the suggestion enables by default.
* `targetRef` is the matching key because it identifies the role representing the incoming access.
Recognizing that role in an existing assignment allows repeated membership reads without creating another assignment each time.
* The correlation item name, `shadowOwner-into-targetRef`, matches the nested mapping that supplies the role reference.

This comparison uses only `targetRef`.
Integrations that distinguish several assignment forms to the same role may need additional correlation settings.

=== Membership Synchronization

Synchronization selects an action based on the matching situation.
Place this block under `inbound/expression/associationSynchronization`, after `correlation`.

.Generated membership synchronization reactions
[source,xml]
----
<synchronization xmlns="http://midpoint.evolveum.com/xml/ns/public/common/common-3">
    <reaction>
        <name>unmatched-add</name>
        <situation>unmatched</situation>
        <actions>
            <addFocusValue/>
        </actions>
    </reaction>
    <reaction>
        <name>matched-synchronize</name>
        <situation>matched</situation>
        <actions>
            <synchronize/>
        </actions>
    </reaction>
    <reaction>
        <name>indirectly-matched-ignore</name>
        <situation>matchedIndirectly</situation>
    </reaction>
</synchronization>
----

A *direct assignment* assigns a role directly to a user.
With *indirect membership*, the user receives that role through another role.
The generated reactions handle these situations:

[cols="20%,25%,55%",options="header"]
|===
| Situation | Generated action | Purpose

| `unmatched`
| `addFocusValue`
| Add an assignment when no corresponding assignment or indirect membership is found.

| `matched`
| `synchronize`
| Synchronize the existing direct assignment instead of adding another one.

| `matchedIndirectly`
| No action
| Leave indirect access without creating a redundant direct assignment.
|===

These rules support importing existing membership and reading back provisioned membership.
Access approvals remain part of the integration's access policy.

== XML Example

The generated association suggestion contains a definition with
the subject and object types, source reference, and mappings
for membership processing.

The following example shows the structure of a suggestion for
`account/default` and `entitlement/app-group`, connected through
the `ri:group` reference.

.Generated association definition (mapping details omitted)
[source,xml]
----
<definition xmlns="http://midpoint.evolveum.com/xml/ns/public/common/common-3"
            xmlns:ri="http://midpoint.evolveum.com/xml/ns/public/resource/instance-3">
    <name>ACCOUNT-default-ref-ENTITLEMENT-app-group</name>
    <displayName>Default Accounts reference to ENTITLEMENT-app-group</displayName>
    <subject> <!--1-->
        <objectType>
            <kind>account</kind>
            <intent>default</intent>
        </objectType>
        <association>
            <ref>group-app-group</ref>
            <sourceAttributeRef>ri:group</sourceAttributeRef> <!--2-->
            <!-- Generated outbound mapping omitted. --> <!--3-->
            <!-- Generated inbound mapping omitted. -->
        </association>
    </subject>
    <object> <!--4-->
        <objectType>
            <kind>entitlement</kind>
            <intent>app-group</intent>
        </objectType>
    </object>
</definition>
----

<1> The subject identifies the account type whose membership is managed.
<2> `sourceAttributeRef` identifies the resource reference used for the association.
The logical association reference `group-app-group` is generated from the source reference and target intent.
<3> The generated outbound and inbound mappings define membership processing.
The inbound mapping also contains correlation and synchronization rules.
<4> The object identifies the target entitlement type.

When the suggestion is accepted and saved, its association
definition becomes part of the resource's association configuration.

== Limitations

* *Simple associations only.*
Complex associations with additional data or multiple object participants are not generated.

* *Supported references only.*
References that do not pass the checks described in <<3. Check Their References>> are skipped.

* *No membership data analysis.*
Suggestions are generated from resource schema definitions and configured object types.
The algorithm does not inspect individual accounts, groups, or their memberships.

* *Business meaning is not evaluated.*
The algorithm identifies technically possible associations but does not determine which relationships should be used to manage access.

* *No automatic membership changes.*
Generating suggestions does not modify existing memberships.
Membership changes require the appropriate configuration and subsequent processing.
